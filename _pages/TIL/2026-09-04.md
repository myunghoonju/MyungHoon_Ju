**배운 점**

- **Filebeat의 kafka output은 이벤트 전체를 JSON으로 감싸서 보냄**
  - Kafka `SimpleProducer`처럼 순수 텍스트를 보내는 것과 달리, Filebeat kafka output은 `{"@timestamp":..., "message": "<원본 로그 라인>", "log":{...}, ...}` 형태로 이벤트 전체를 JSON 직렬화해서 보냄
  - Logstash에서 바로 `grok`을 걸면 이 바깥 JSON 문자열 전체를 대상으로 매칭 시도해서 100% `_grokparsefailure` — `json { source => "message" }` 필터로 먼저 언랩해서 안쪽의 진짜 로그 라인이 `message`를 덮어쓰게 만들어야 함

- **인덱스 이름은 좁게 스코프해서 짓기**
  - `weblog-%{+YYYY.MM.dd}`라는 흔한 이름을 새로 쓰다가, 며칠 전 Phase 5 테스트(`file-input-test.conf`, `beats-input-test.conf`)가 이미 같은 이름을 쓰고 있어서 완전히 다른 데이터가 같은 인덱스 패턴에 섞여버림 — 오래 켜두는 ES 클러스터에서는 일반적인 이름(`weblog`, `test` 등)을 재사용하면 이렇게 조용히 충돌함

- **`geo_point` 매핑은 데이터 적재 *전에* 반드시 지정**
  - 매핑 템플릿 없이 문서를 먼저 넣으면 Elasticsearch 동적 매핑이 `geoip.location`을 그냥 숫자 객체로 잡아버려서 Coordinate Map에서 필드 선택 자체가 안 됨(Phase 4의 `geo.coordinates` 교훈을 또 까먹음)
  - `PUT _template/...`로 매핑 지정 후 인덱스를 새로 만들어야 하고(기존 문서엔 소급 적용 안 됨), Kibana의 index pattern도 필드 타입을 생성/마지막 refresh 시점에 캐시해두므로 매핑을 바꾼 뒤엔 Stack Management에서 수동으로 "Refresh field list" 해줘야 반영됨

- **Kafka를 Filebeat–Logstash 사이 버퍼로 넣는 패턴**
  - `nginx access.log → Filebeat(output: kafka) → Kafka topic → Logstash(kafka input) → Elasticsearch`처럼 중간에 Kafka를 끼우면, Logstash/ES가 잠깐 죽어도 Kafka가 로그를 유실 없이 버퍼링해준다는 실무 패턴을 직접 구성해봄 — Phase 5b에서 만든 `kafka` input 패턴을 그대로 재사용 가능했음
