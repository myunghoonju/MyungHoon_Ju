**한 일**
- [line/armeria](https://github.com/line/armeria) 소스에서 본 `@UnstableApi` 커스텀 애너테이션을 라인별로 분석
- `@Retention`, `@Target`, `@Documented`의 역할과, `RetentionPolicy` 3종(`SOURCE`/`CLASS`/`RUNTIME`)의 차이를 정리

**배운 점**

- **분석 대상 코드 (armeria)**
  ```java
  @Retention(RetentionPolicy.CLASS)
  @Target({
          ElementType.ANNOTATION_TYPE,
          ElementType.CONSTRUCTOR,
          ElementType.FIELD,
          ElementType.METHOD,
          ElementType.PACKAGE,
          ElementType.TYPE
  })
  @Documented
  public @interface UnstableApi {
  }
  ```
  - `@Target`: 이 애너테이션을 붙일 수 있는 위치 제한 (애너테이션 자체, 생성자, 필드, 메서드, 패키지, 타입)
  - `@Documented`: Javadoc 생성 시 이 애너테이션이 붙은 요소의 문서에 애너테이션 자체도 표시됨
  - 멤버 없는 마커 애너테이션 — "이 API는 아직 불안정하다"는 표시 용도

- **`RetentionPolicy` 3종 — 언제까지 정보가 살아남는가**
  | Policy | 남는 범위 | 런타임 리플렉션 | 예시 |
  |---|---|---|---|
  | `SOURCE` | `.java`까지만, 컴파일 시 소멸 | 불가 | `@Override`, `@SuppressWarnings` |
  | `CLASS` (기본값) | `.class` 파일까지 남음 | 불가 | Lombok 계열 |
  | `RUNTIME` | `.class` + 런타임 리플렉션 가능 | 가능 | `@Autowired`, `@Test` |

- **`.class` 파일 내부 구조 — `SOURCE` vs `CLASS`의 차이를 만드는 지점**
  - `.class`는 애너테이션을 두 테이블로 나눠 저장: `RuntimeVisibleAnnotations`(RUNTIME) / `RuntimeInvisibleAnnotations`(CLASS)
  - JVM은 클래스 로드 시 파일 전체를 메모리에 올리지만, `java.lang.reflect` API 스펙 자체가 `RuntimeInvisibleAnnotations`는 리플렉션 결과에서 제외하도록 정의되어 있음
  - 즉 "`.class`에 존재한다" ≠ "런타임에 `getAnnotations()`로 읽힌다" — 파일엔 남지만 표준 리플렉션 API에서는 의도적으로 숨겨짐
  - `javap -v Foo.class`로 직접 열어보면 `SOURCE` 애너테이션은 흔적도 없고, `CLASS` 애너테이션은 `RuntimeInvisibleAnnotations`에 남아있는 걸 확인 가능

- **`CLASS`는 누가, 왜 읽는가**
  - 표준 리플렉션 API로는 못 읽지만, `.class` 바이트를 직접 파싱하는 도구(ASM, ByteBuddy, javassist, 정적분석기/린터, IDE 인스펙션)는 이 필터링을 거치지 않으므로 그대로 읽을 수 있음
