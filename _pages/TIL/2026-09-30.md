**한 일**
- `jdk.internal.vm.Continuation`으로 가상 스레드를 직접 흉내 내는 커스텀 구현 작성 (`CustomVirtualThread`, `CustomVirtualThreadScheduler`, `FileIoSample`, `CustomVtRunner`)
- 가상 스레드의 carrier 풀과 비교하기 위해 `BlockingQueue` 기반 고정 크기 스레드 풀 직접 구현 (`SimpleThreadPool`, `SimpleThreadPoolDemo`)
- `VarHandle.compareAndSet` CAS 루프로 락 없는 카운터 구현 (`AtomicCounter`)

**배운 점**

- **가상 스레드 = Continuation + 스케줄러(carrier 풀)**
  - `CustomVirtualThread`는 `Continuation(SCOPE, runnable)`을 들고 있고, `run()`은 `continuation.run()`만 호출 — JDK의 `VirtualThread`도 내부에 Continuation을 들고 있는 같은 구조
  - `CustomVirtualThreadScheduler`의 `newWorkStealingPool(2)`는 JDK의 carrier 풀(`ForkJoinPool`, 기본 병렬도 = CPU 코어 수) 역할
  - `CURRENT_VT` ThreadLocal을 mount할 때 set, unmount할 때 remove해서 "지금 이 carrier에 올라탄 VT"를 흉내 냄 — JDK는 `Thread.currentThread()`가 carrier 대신 VT를 반환하도록 교체하는 방식
  - `IO_EVENT_SCHEDULER`(ScheduledExecutor)는 JDK의 `Poller` 스레드(epoll/kqueue)나 sleep 타이머 역할 — IO가 끝나면 `SCHEDULER.schedule(current)`로 continuation을 풀에 다시 제출하는 것이 JDK의 `unpark()`에 해당

- **`Continuation.yield()`는 "일시정지", `run()` 재호출은 "재개"**
  - yield 지점은 `FileIoSample.transfer()` 안의 딱 한 군데 — VT마다 1회, 작업 4개면 전체 4회
  - yield하면 스택 프레임이 힙에 저장되고, 제어권은 **main 스레드가 아니라 `continuation.run()`을 호출한 carrier(worker) 스레드**로 돌아감 (`thread.run()` 다음 줄) → worker는 풀려나서 큐의 다음 작업을 집음
  - 그래서 "Completed" 로그는 yield 때가 아니라 IO 완료 후 **재개된 뒤에** 찍힘 — 람다 하나가 yield 전후로 두 번의 `run()`에 나뉘어 실행됨
  - 재개는 그 시점에 비어 있는 **아무 worker**가 맡으므로 "Running"과 "Completed" 로그의 스레드 이름이 다를 수 있음
  - worker가 2개라 처음 두 작업은 동시에 실행되고, 나머지 두 개는 큐에서 대기하다가 앞의 작업이 yield하면 그 worker에서 실행됨

- **커스텀 구현과 실제 가상 스레드의 차이**
  - JDK는 `socket.read()`, `Thread.sleep()`, `lock()` 같은 블로킹 API 안에서 알아서 park/yield함. 커스텀 구현은 사용자 코드가 직접 `yield`를 호출해야 함
  - 경쟁 조건: 콜백을 등록한 뒤 yield가 끝나기 전에 콜백이 먼저 실행되면(`nextInt(1000)`이 0일 때 등), 아직 mount된 continuation을 다른 worker가 `run()`할 수 있음. JDK는 `PARKING → PARKED` 상태를 CAS로 전이해서 이 상황을 처리함
  - pinning(native 프레임 등이 스택에 있어 yield 불가) 처리는 없음

- **`SimpleThreadPool` — 고정 크기 스레드 풀의 기본 구조**
  - `BlockingQueue<Runnable>`(용량 제한)에 작업을 `put`하고, `Worker` 스레드들이 `while (running)` 루프에서 `take()` → `run()` 반복
  - 큐가 가득 차면 `put()`이 블로킹되어 제출하는 쪽이 자연스럽게 속도 조절(backpressure)됨
  - `ThreadGroup`으로 worker를 묶어두면 `threadGroup.interrupt()` 한 번으로 `take()`에서 대기 중인 worker를 전부 깨워 종료 가능
  - `AutoCloseable`로 만들어 try-with-resources 블록이 끝나면 큐가 빌 때까지 기다린 뒤 shutdown
  - 주의: 큐가 비었다고 작업이 끝난 건 아님 — 마지막으로 꺼낸 작업들이 `Thread.sleep()` 중일 때 `interrupt()`가 들어가면 그 작업들이 중간에 끊김
  - 플랫폼 스레드 풀은 스레드가 블로킹되면 그 스레드가 그대로 묶여 있음 — 가상 스레드는 블로킹 지점에서 unmount되어 carrier를 반납한다는 점이 핵심 차이

- **`VarHandle` CAS로 락 없이 카운터 증가**
  - `MethodHandles.lookup().findVarHandle(AtomicCounter.class, "counter", int.class)`로 `volatile int` 필드의 핸들을 얻음
  - `do { current = counter; next = current + 1; } while (!COUNTER_HANDLE.compareAndSet(this, current, next));` — 읽은 값이 그 사이에 바뀌었으면 CAS가 실패하므로 다시 읽고 재시도
  - `AtomicInteger.incrementAndGet()`이 내부적으로 하는 일과 같은 원리 (락 대신 CPU의 CAS 명령 사용)
