**한 일**
- BFF, API Gateway, OAuth2, 프록시 개념 정리

**배운 점**

- **API Gateway vs BFF**
  - API Gateway: 모든 클라이언트가 공유하는 단일 진입점. 라우팅, 인증, rate limiting 등 횡단 관심사(cross-cutting concerns) 처리. 클라이언트 종류에 무관(generic)
  - BFF: 클라이언트(웹/모바일/파트너)마다 전용으로 두는 백엔드. 여러 마이크로서비스 응답을 조합(aggregation)해서 클라이언트에 맞는 형태로 가공. 프론트엔드 팀이 소유하는 경우가 많음
  - 실무에서는 둘을 함께 씀: `Client → BFF(클라이언트별) → API Gateway → Microservices`

- **BFF의 코드 중복은 어디서 발생하는가**
  - Gateway(보통 1개)나 마이크로서비스 자체가 아니라, **여러 BFF가 같은 마이크로서비스 집합을 각자 호출/조합하는 오케스트레이션 로직**에서 발생
  - 완화 방법: 공유 클라이언트 SDK화, GraphQL Gateway로 대체, BFF를 얇게 유지하고 공통 로직은 Gateway/서비스 메시로 위임

- **Authorization Server vs Resource Server**
  - Authorization Server: 토큰 발급 담당 (Keycloak, Auth0, Okta 등). 인증 로직(비밀번호, MFA)에 집중, 보통 별도 서버로 중앙화
  - Resource Server: 토큰 검증 + 실제 API 제공. JWT는 self-contained라 Authorization Server에 매번 묻지 않고 공개키로 로컬 검증 가능 (stateless)

- **전체 흐름 예시**
  - 토큰 발급: `Client → Authorization Server` (Gateway를 거치지 않는 별도 경로)
  - API 요청: `Client → API Gateway(1차 Resource Server 역할) → Microservices(내부에서 재검증하기도 함)`
  - 검증 책임 분리 패턴: Gateway에서만 검증(단순하지만 내부 침투에 취약) vs 각 서비스도 Zero Trust로 재검증(안전하지만 약간의 오버헤드)

- **Forward Proxy vs Reverse Proxy**
  - Forward Proxy: **클라이언트를 대신**함. 클라이언트(브라우저/OS)가 프록시 존재를 알고 명시적으로 "이거 대신 가져다줘" 요청. 서버는 진짜 클라이언트를 모름 (클라이언트를 숨김)
  - Reverse Proxy: **서버를 대신**함. 클라이언트는 프록시를 진짜 서버라고 착각하고 평범하게 요청. 클라이언트는 뒤에 몇 대의 서버가 있는지 모름 (서버를 숨김)
  - API Gateway는 Reverse Proxy의 특수화된 형태 (라우팅/로드밸런싱 + 인증/rate limiting 등 API 특화 기능 추가)
