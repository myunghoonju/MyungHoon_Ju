**배운 점**

- **`SseEmitter`와 비동기 요청 처리**
  - 컨트롤러가 `SseEmitter`를 리턴하면 Spring이 요청을 비동기 모드(Servlet `AsyncContext`)로 전환함
  - 컨트롤러 메서드가 끝나도 HTTP 커넥션은 열린 채 유지되고, 그 요청을 처리하던 워커 스레드만 풀로 반납됨
  - 실제 이벤트 전송(`emitter.send(...)`)은 별도 스레드(가상 스레드)에서 그 열린 커넥션에 데이터를 흘려보내는 방식 — 워커 스레드는 "커넥션 셋업" 역할, 별도 스레드는 "데이터 전송" 역할로 분리됨
  ```java
  @GetMapping(value = "/sse/hello", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
  public SseEmitter hello() {
      SseEmitter emitter = new SseEmitter(5_000L);
      executor.execute(() -> {
          for (int i = 1; i <= 3; i++) {
              try {
                  emitter.send(SseEmitter.event().name("MESSAGE").data("event " + i));
                  Thread.sleep(1000);
              } catch (IOException e) {
                  emitter.completeWithError(e);
                  return; // break가 아니라 return이어야 람다 전체를 빠져나가 아래 complete()가 또 호출되는 걸 막음
              } catch (InterruptedException e) {
                  Thread.currentThread().interrupt();
                  emitter.completeWithError(e);
                  return;
              }
          }
          emitter.complete();
      });
      return emitter;
  }
  ```

- **자주 하는 실수: `break` vs `return`**
  - `executor.execute(() -> { for (...) { try { ... } catch (...) { emitter.completeWithError(e); break; } } emitter.complete(); })` 구조에서 `break`는 `for` 루프만 빠져나감
  - 람다 본문 끝의 `emitter.complete()`가 그대로 실행돼서, 에러로 이미 종료된 emitter에 또 `complete()`를 호출하는 버그가 남음
  - `break` 대신 `return`을 써야 람다 자체를 즉시 빠져나가 중복 호출을 막을 수 있음

- **가상 스레드 (Java 25 + Spring Boot 4)**

- **SSE 스트리밍 검증 방법별 차이**
  - `curl -N`: 버퍼링을 끄고 도착하는 즉시 한 줄씩 출력 → 실시간성 확인에 적합
  - 브라우저 직접 접속: 응답을 점진적으로 렌더링해서 텍스트가 실시간으로 하나씩 찍힘
  - Chrome DevTools Network 탭의 **EventStream** 서브탭: `Content-Type: text/event-stream`이면 자동으로 생기고, 각 이벤트의 도착 시각을 개별 행으로 보여줌 (Timing 탭의 Content Download 구간이 전체 스트림 지속시간과 일치하는 것도 커넥션이 계속 열려있었다는 증거)
  - HTTPie **데스크톱 앱**은 응답을 전부 받은 뒤 한꺼번에 렌더링해서 스트리밍이 안 보임 — 도구 자체의 한계이지 서버 문제가 아님 (반면 HTTPie CLI는 `-S`/`--stream` 옵션으로 실시간 출력 가능)

- **`fetch` + `ReadableStream`으로 SSE 직접 파싱**
  - `response.body`가 `ReadableStream`, `reader.read()`로 `Uint8Array` 청크를 받아 `TextDecoder`로 문자열 변환
  - 네트워크 청크는 이벤트 경계와 무관하게 잘려서 옴 — 받은 텍스트를 계속 `buffer`에 누적하다가 `\n\n`(빈 줄)이 나오면 그때까지가 완성된 이벤트, 나머지는 버퍼에 남겨 다음 청크와 이어붙임
  ```js
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });

    let boundary;
    while ((boundary = buffer.indexOf('\n\n')) !== -1) {
      const block = buffer.slice(0, boundary);
      buffer = buffer.slice(boundary + 2);
      const { name, data } = parseEventBlock(block);
      log(`[${name}] ${data}`);
    }
  }
  ```

- **WHATWG SSE 스펙 필드 파싱 (처음 버전과의 차이)**
  - `data:` 줄이 한 이벤트 안에 여러 개면 마지막 줄로 덮어쓰지 말고 `\n`으로 이어붙여야 함
  - `:`로 시작하는 줄은 필드가 아니라 주석/keep-alive용이므로 통째로 무시
  - `event:` 필드가 없으면 기본 이벤트 타입은 `"message"`
  - 실무에서는 이런 파서를 직접 짜기보다 `@microsoft/fetch-event-source` 같은 라이브러리 사용 — `id:`/`retry:` 필드, 재연결(backoff), `AbortController` 정리까지 처리해줌 (지금 짠 코드는 그 라이브러리 내부 동작을 이해하기 위한 실습)

- **`CompletableFuture.whenComplete` — 왜 `allOf().join()`이 아닌가**
  - `CompletableFuture.allOf(f1, f2, f3).join()`은 셋 다 끝날 때까지 기다렸다가 한 번에 처리 → 빠른 섹션(FAST)이 이미 끝났어도 느린 섹션(SLOW)까지 기다려야 클라이언트에 아무것도 못 보냄. SSE로 병렬 스트리밍하는 목적 자체가 무의미해짐
  - `future.whenComplete((result, error) -> {...})`는 블로킹 없이 콜백만 등록 — 각 future가 **자기가 끝나는 시점에 독립적으로** 콜백 실행
  ```java
  future.whenComplete((result, error) -> {
      emitter.send(SseEmitter.event().name("SECTION").data(result));
  });
  ```
  - 전체 완료 감지(마지막에 `DONE` 이벤트 보내기)는 `CompletableFuture.allOf(f1, f2, f3).whenComplete(...)`로 — `join()`처럼 블로킹하지 않으면서 "셋 다 끝난 시점"만 콜백으로 받음
